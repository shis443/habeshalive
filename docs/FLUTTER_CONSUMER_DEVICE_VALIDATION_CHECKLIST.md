# Birq Flutter Consumer — Physical-Device Validation Checklist

For the project owner. Everything up to this point (environment hardening,
Debug/Release framework embedding, an unsigned Release archive, and a full
local integration-test pass) was done in the Simulator, in a sandboxed
environment with no Apple Developer credentials and no physical device.
This checklist is what's left before the app can be considered validated
on real hardware. Nothing here deploys anything — it's all local
Xcode/device setup.

**Do not upload to TestFlight or the App Store as part of this checklist.**
That's a separate, later decision once everything below passes.

---

## 1. Xcode Signing & Capabilities

1. Open `Birq.xcodeproj` in Xcode (not the `.xcworkspace` — this project
   has no CocoaPods workspace; it's Swift Package Manager).
2. Select the **Birq** target → **Signing & Capabilities** tab.
3. Confirm **Automatically manage signing** is checked.
4. Under **Team**, select your own Apple ID / Apple Developer Team — not
   the placeholder Team ID already in the project (`Y24W9474LJ`), unless
   that's actually yours. If it's not yours, Xcode will show a signing
   error and you'll need to pick your own team from the dropdown (sign
   into Xcode with your Apple ID first via **Xcode → Settings →
   Accounts** if you haven't).
5. Bundle identifier is `com.birq.mobile`. If your Apple ID's team doesn't
   already have this bundle ID registered, Xcode will offer to register
   it automatically the first time you build — that's expected and fine
   for a free personal team too, no paid membership required for local
   device testing.
6. Repeat for the other real targets in this project if you plan to test
   them: **BirqLiveActivity** (`com.birq.mobile.LiveActivity`), **Birq
   Screen Recording**, **BirqWatch** — each needs its own bundle ID
   registered the same way. For a first validation pass, only the main
   **Birq** target matters.

## 2. Apple Developer Team / provisioning

- A **free** Apple ID works for installing and running on your own device
  for local testing (7-day provisioning-profile expiry, needs
  re-installing from Xcode weekly).
- A **paid** Apple Developer Program membership ($99/year) is only needed
  for: longer-lived provisioning, real Push Notifications, and eventually
  TestFlight/App Store — none of which this checklist requires.
- Provisioning profiles are auto-generated by Xcode once signing is set
  up (§1) and a device is connected (§3) — no manual portal work needed
  for local testing.

## 3. Developer Mode / device trust (iOS 16+)

1. Connect the iPhone to your Mac via cable (first time) or ensure it's
   on the same Wi-Fi network (for wireless debugging afterward).
2. In Xcode, **Window → Devices and Simulators**, confirm the device
   appears and is recognized.
3. On the device: **Settings → Privacy & Security → Developer Mode** →
   toggle on → the phone will prompt to restart → after restart, confirm
   "Turn On" when prompted.
4. Build and install once from Xcode (⌘R with the device selected as the
   run destination).
5. First launch will fail with an "Untrusted Developer" prompt. On the
   device: **Settings → General → VPN & Device Management** → tap your
   Apple ID under Developer App → **Trust**.
6. Re-launch from Xcode or tap the app icon directly — it should open
   normally now.

## 4. Required permissions (already declared — nothing to add)

These are already correctly declared in the app's build settings, so iOS

during testing:

| Permission | Declared string |
| --- | --- |
| Camera | "Birq live streams video from the camera." |
| Microphone | "Birq live streams audio from the microphone." |
| Local Network | "Birq uses localhost as input and output to SRT library." |

The Local Network permission is the one to watch for specifically when
testing the Flutter consumer flows below against a local backend — see
§5's note on device-vs-Simulator networking.

## 5. Which backend to point the device at

**This is the one step most likely to trip you up if skipped.**

On the Simulator, `localhost` transparently reaches your Mac — that's how
every local-backend test this session ran. On a **physical device**,
`localhost` means the phone itself, not your Mac. A Debug build installed
as-is will try to reach `http://localhost:4000` and every API call will
fail with a connection error.

Two options:

**Option A — test against your Mac's local backend (recommended first
pass, matches everything already verified this session):**

1. Make sure your Mac and iPhone are on the same Wi-Fi network.
2. Find your Mac's LAN IP: `ipconfig getifaddr en0` in Terminal (or
   **System Settings → Wi-Fi → Details → IP Address**).
3. Rebuild the Flutter frameworks with that IP baked in (dart-defines are
   compiled into the framework, not read at runtime):
   ```bash
   cd flutter_consumer
   flutter build ios-framework --output=Flutter/ \
     --dart-define=BIRQ_ENV=staging \
     --dart-define=BIRQ_API_BASE_URL=http://<your-mac-ip>:4000 \
     --dart-define=BIRQ_CENTRIFUGO_WS_URL=ws://<your-mac-ip>:8000/connection/websocket \
     --dart-define=BIRQ_WEB_URL=http://<your-mac-ip>:3000
   ```
4. Make sure the local stack is actually running on your Mac: `apps/api`
   (`npm run dev`), Postgres, Redis, and (for chat/live playback)
   `docker compose up -d redis centrifugo`. See
   `docs/FLUTTER_CONSUMER_ARCHITECTURE.md § 9` for exactly how this
   session set that up, including two local-only test accounts you can
   reuse (`birq.local.viewer@example.com` / `birq.local.test@example.com`,
   password `BirqLocalTest123!`) — or create your own via the app's real
   sign-up flow.
5. Rebuild and reinstall the native app from Xcode after the framework
   rebuild.
6. The on-screen debug banner (Debug builds only) will confirm which
   backend it's actually hitting — check it reads your Mac's IP, not
   `localhost` or `api.birq.live`.

**Option B — test against real production (your own call, not something
I did this session):** a Release build defaults to `https://api.birq.live`
with no dart-define needed. If you go this route, be aware you're using
your own real Birq account and real data — nothing in this checklist
assumes or requires that.

## 6. Flows to test

Everything below was verified in the Simulator via automated
`integration_test` runs against a local backend (see the architecture
doc § 9/10 for exact results) — this pass is about confirming the same
behavior holds on real hardware with a real touchscreen, real camera/mic,
and real network conditions.

**Public / signed-out:**
- [ ] App launches to Explore without hanging on the splash screen
- [ ] Explore shows real live streams (or a real "Nothing live right
      now" empty state) and real category chips
- [ ] Tap Discover, Browse, a category card, Search — each opens and has
      a working close/back button (all four were specifically fixed
      this session for exactly this — confirm they don't trap you)
- [ ] Search a real term, tap a result, land on Watch
- [ ] Tapping a protected tab (Following/Wallet/Profile) while signed
      out redirects to the one shared login screen — confirm there's a
      close (X) button that returns you to Explore without signing in

**Sign-in and identity:**
- [ ] Log in with a real account (local test account or your own)
- [ ] Signing in from a protected-tab redirect lands back on that exact
      tab, not just Explore
- [ ] Profile shows real account data; tap the pencil next to Bio, edit
      it, Save — confirm it persists after leaving and returning
- [ ] Log out — confirm you land back on the login screen with a way
      back to Explore

**Following / Wallet / Activity:**
- [ ] Following tab shows real followed creators or a real empty state
- [ ] Wallet shows a real balance and real transaction history
- [ ] Activity (notification bell from Profile) shows real notifications;
      "Mark all read" actually clears the unread markers

**Watch (the real functional core):**
- [ ] Open a live stream — real HLS video actually plays, not a static
      image
- [ ] Chat messages you send actually appear (round-tripping through the
      real Centrifugo connection, not an optimistic local echo — you
      should see a brief delay, not instant)
- [ ] Follow/unfollow the creator from Watch — button state updates
- [ ] If you have a PPV-gated stream available: confirm the lock screen
      shows, buying access deducts your real wallet balance and unlocks
      playback

**Go Live handoff (native, not Flutter):**
- [ ] Tap Go Live from Explore's bottom nav — real camera preview and
      mic permission prompts appear (native Swift stack, unchanged by
      this Flutter work)
- [ ] Close/end the Go Live flow — confirm you land back in Flutter at
      wherever you were before, not a blank or crashed screen

**General:**
- [ ] Switching tabs (Explore/Following/Wallet/Profile) feels instant —
      no reload flash, scroll position holds when you switch away and back
- [ ] With iOS Reduce Motion on (**Settings → Accessibility → Motion**),
      transitions become an instant cut instead of a fade, nothing hangs
- [ ] Backgrounding and reopening the app restores your session (still
      signed in, still on the same screen)

## 7. If something breaks

Note which checklist item failed, what you actually saw (screenshot if
possible), and whether the debug banner showed the backend you expected.
That's the fastest way to tell a real regression apart from a
backend-target mixup (§5).
