### 3.4 BIRQ security audit & hardening — 2026-08-04 (independently verified)

Full file:line audit of `apps/api`, `apps/web`, `db/migrations`, `infra/`,
and `centrifugo/` against all 11 items in the BIRQ guidelines' Part III.
Shipped and deployed (commits `d44666c`, `ba82ff5`, `96a7da0`, `512997d`):

- **VOD playback URLs** are short-lived presigned R2 URLs, not permanent
  public links (`common/object-storage.ts`, `vods/service.ts`).
- **Stream-key comparison** uses `timingSafeEqual`, was a plain `!==`
  (`streams/service.ts`).
- **`requireAdmin`** re-checks `users.role` from the database on every
  request instead of trusting the JWT claim (`app.ts`) — closes a
  privilege-outlives-revocation gap.
- **HLS latency**: `hls_fragment` 4s→2s, `hls_window` 30s→10s
  (`infra/srs/conf/srs.conf.template`). Deployed with the standard
  no-live-viewers safety check.
- **Sentry** wired into the global error handler and every background
  job's failure path on the API side (`common/sentry.ts`); `@sentry/nextjs`
  added on the web side. Both stub-vs-real gated on the DSN env var.
- **Temporal-backed durable payout workflow**: reserve funds → wait for
  manual-review signal if needed → Chapa transfer → wait for the
  transfer-webhook's completion signal → settle. Idempotent activities,
  payout ID doubles as the workflow ID (`wallet/temporal/`).
- **Two full staged plans written, infra not yet executed at the time**:
  `docs/egress-protection-plan.md` (Cloudflare Tunnel + Worker + WAF) and
  `docs/temporal-migration-plan.md` (full risk audit + rollout plan).
- **Deliberately not built, with reasoning documented**: Chapa webhook
  timestamp validation — Chapa's actual webhook contract carries no
  timestamp field to validate against; the existing `tx_ref` idempotency
  check is the real, correct defense here.

Also shipped same window: the gift-card delivery Temporal workflow
(`gift-cards/temporal/`, same dormant-until-configured pattern as
payouts), and the HLS viewer-token gate (API-side HS256 token minting +
a Cloudflare Worker that validates it and rewrites manifests — commit
`1e21392`).

### 3.6 Critical fix: SRS admin API was publicly exposed — 2026-08-05 (independently verified)

Found while verifying the WHEP task's own stated precondition ("keep
`/api/v1/` internal"): direct testing against the live `habeshalive-srs`
machine found `GET https://habeshalive-srs.fly.dev:8443/api/v1/clients/`
returning **HTTP 200 with real connected-client data, completely
unauthenticated** — anyone could enumerate, and via `DELETE`, kick any
connected publisher. This is SRS's admin surface sharing the exact same
public port as WHIP publish signaling, with no path-scoped ACL of its own
(confirmed against SRS's own source code, not assumed) and no way to
protect it with SRS's built-in Basic Auth without also breaking public
WHIP publish.

**Fix** (commit `516e06c`, its own commit, shipped and deployed
independently of the WHEP work below): `infra/srs/conf/whip-proxy.nginx.conf`
— a minimal nginx reverse proxy in front of SRS's `http_api` port,
allow-listing only `/rtc/v1/whip/` and returning `403` for everything
else, including `/api/v1/*`. `fly.toml`'s public WHIP service now points
at this proxy instead of SRS's real port directly.

**Verified live**: `curl -I https://habeshalive-srs.fly.dev:8443/api/v1/clients/`
now returns `403`. SRS's own server logs confirm legitimate WHIP traffic
is still correctly proxied through untouched. No live viewers/publishers
were affected — `/streams/live` was empty before the machine restarted.

### 3.7 WHEP (WebRTC) low-latency playback — 2026-08-05 (independently verified, ships inert)

Full architecture/security design was reviewed and approved before any
code was written, per the BIRQ guidelines. Adds a sub-2s WebRTC playback
path alongside the existing HLS pipeline. Commit `a9e7784`.

- **Infra**: `rtmp_to_rtc on`, `rtc_server.tcp` + `protocol all`
  (WebRTC-over-TCP fallback for networks that block UDP), matching
  `fly.toml` TCP service mapping.
- **Backend broker** (`apps/api/src/streams/whep-routes.ts`): brokers the
  SDP offer/answer **server-to-server to SRS over Fly's private network**
  (new `SRS_ADMIN_API_BASE` env var) rather than exposing SRS's own
  `/rtc/v1/whep/` publicly — stricter than literally requested ("expose
  only `/rtc/v1/whep/`"), since the broker pattern means WHEP never needs
  a public SRS endpoint at all. Live ban check, 5/min rate limit, a
  global concurrency ceiling checked before brokering.
- **Session registry** (`whep-session-registry.ts`): Redis-backed, no DB
  migration needed.
- **Ban-teardown**: `moderation/actions-service.ts`'s `banUser` now tears
  down a banned viewer's active WHEP session(s) — same pattern as the
  pre-existing Centrifugo-chat-disconnect-on-ban, extended to this new
  media path.
- **Frontend**: `apps/web/lib/whep-client.ts` (native `RTCPeerConnection`
  client) + `VideoPlayer.tsx` rewritten as a state machine — starts in a
  `whep` engine, falls back one-directionally to the existing, unmodified
  hls.js/native-HLS logic on a 3s connect timeout or an immediate ICE
  `failed`.
- **A real dependency bug found and fixed along the way**: `apps/web`'s
  `/api/backend` proxy hard-401'd every request with no session cookie —
  would have silently broken WHEP for every logged-out viewer (a normal,
  expected class of user here). Changed to forward without an
  `Authorization` header instead, letting each backend route's own
  `authenticate`/`tryAuthenticate` decide.

**Ships fully inert**: `WHEP_ENABLED` (API) and `NEXT_PUBLIC_WHEP_ENABLED`
(web) both default off — confirmed unset in production today via
`flyctl secrets list` / `vercel env ls`, not assumed. Both apps are
deployed with this code; `/streams/:id/whep` correctly returns `503`
(registered, refusing), not `404`.

**What cannot be verified in this environment** (no browser, camera, or
real network path available): real WebRTC/ICE/media behavior. Written up
as a concrete pre-activation checklist in `docs/whep-rollout.md` — iOS
Safari, Android Chrome, a UDP-restricted network, and a live ban-teardown
test. **None of this has run yet.**

out of this repo" per `docs/egress-protection-plan.md`, used only for
one-off setup calls. Separate and distinct from `CLOUDFLARE_TUNNEL_TOKEN`
(a real Fly secret on the SRS app), which was **not** part of this
