## 1. Security audit (Part III of the BIRQ guidelines)

Ran a file:line audit of `apps/api`, `apps/web`, `db/migrations`, `infra/`,
and `centrifugo/` against all 11 items. Full findings were reported
inline in this session; the ones that led to code changes are covered in
§2 below. Notable results not otherwise covered:

- **Compliant, no action needed**: app-layer authorization (no Supabase/
  native RLS in this stack — confirmed via `docs/SECURITY.md`), frontend
  secret exposure, WebSocket chat rate limiting, real-time ban
  enforcement, parameterized queries (no SQL injection surface found).
- **N/A, feature doesn't exist**: VOD/clip DoS protection (no `ffmpeg`
  anywhere in the codebase), WebRTC peer-to-peer IP leakage (WHIP ingest
  only, no viewer-facing WebRTC).
- **Chapa webhook timestamp validation — investigated, deliberately not
  built.** Chapa's actual webhook contract (`chapaWebhookSchema` in
  `packages/shared/src/schemas/wallet.ts:152-157`) carries no timestamp
  field, and neither does the `x-chapa-signature` header. There is
  nothing to validate a time window against — a check against "time since
  our server received it" wouldn't distinguish a legitimate Chapa retry
  from a replay attack, so it would be security theater, not a real
  control. The existing `tx_ref` idempotency check
  (`wallet/service.ts`'s `completePayoutFromWebhook`) is the actual,
  correct defense here, and was already in place before this session.

  The payout half is now *implemented* (§2) — gift-card delivery and
  subscription renewal are still plan-only.
- **`docs/hls-latency-testing.md`** — manual testing checklist for the

  a realistic latency expectation (~6-12s is normal, not a bug — sub-5s
  needs WebRTC/WHEP, a different mechanism, not further HLS tuning).
  **Nobody has run this yet** — the results template is empty.
